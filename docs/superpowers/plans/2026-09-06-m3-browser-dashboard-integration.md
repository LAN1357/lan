# M3 浏览器经营分析看板整合计划

日期：2026-09-06。状态：代码已实施并通过合成账例自动化与浏览器检查，待财务BP真实试用确认。依据：M3只读分析设计、当前M2/M3代码，以及用户对共同契约、只读路由、版本行为、诊断展示和实施顺序的补充确认。

## 1. 目标与核心决定

在现有本地工作台的同一HTTP服务和端口中增加M3经营分析看板。浏览器以结构化看板为主，不增加聊天框；自然语言查询、连续追问和复盘草稿继续由Codex、Claude Code等Agent Harness通过现有stdio MCP完成。

最终结构：

```text
M2关账发布 ──> closes不可变副本
                     │
              M3共同分析服务
              ├── Web只读适配 ──> 浏览器看板
              └── MCP只读适配 ──> Codex / Claude Code
```

“共同核心”同时覆盖计算、参数默认值和结果契约。Web与MCP不得分别解释月份、版本、分页、排序、金额、比率、不适用值或错误码。浏览器只展示后端结果，不在JavaScript中求和、计算利润率、重新排名或从当前页推导全量结果。

## 2. 本轮范围

### 2.1 交付内容

- 三个一级入口：月份总览、结算工作台、经营分析。
- M3经营概览、重点场次、场次/达人筛选与复制分析引用。
- 场次利润、SKU直接贡献、分配和修改依据下钻。
- 期间比较与同月关账版本比较，使用两个不同契约和页面区域。
- 明确费用、SKU单位成本的非持久化条件测算表单。
- 八项只读HTTP接口，与八个MCP工具调用同一应用服务。
- Web/MCP输入、输出、默认值和错误行为一致性测试。
- 继续限制服务只监听本机；现有M2写操作、M3 MCP和正式Excel保持可用。

### 2.2 明确不做

- 不在浏览器增加模型、聊天、提示词、对话历史或API密钥管理。
- 不增加独立微服务、消息队列、任务系统、缓存表或新的分析数据库。
- 不把MCP stdio服务嵌进HTTP进程；HTTP不依赖MCP SDK。
- 不建设登录、角色、公司内网访问、云部署或多人并发写入。本轮仍为本机单用户服务。
- 不让M3修改归属、费用、业务范围、关账版本或正式Excel。
- 不在前端复制利润公式、异常规则或条件测算逻辑。

多人共享部署另立后续阶段，届时单独设计身份、只读/写入角色、网络边界、HTTPS、备份和并发写入策略。

## 3. 当前代码约束与改造原则

### 3.1 必须绕开的写连接入口

当前`src/workbench/app.py`的`Handler.do_GET`和`Handler.do_POST`在识别具体路由前调用`src.workbench.db.connect()`。该连接允许建库和结构升级，不能作为M3页面或分析API的入口。

改造后请求顺序必须为：

```text
校验Host/Origin
  ├── 命中 /analysis、/analysis/scenario（页面POST）、/analysis.js、/api/analysis/*
  │      └── 使用固定路径CloseReader，直接返回；不得调用workbench.connect()
  └── 其他M2/总览/导出路由
         └── 按现有规则使用workbench.connect()
```

可以复用同一个`ThreadingHTTPServer`和端口。`WorkbenchServer`在启动时保存固定数据库路径并构造不发生I/O的分析服务对象；每个分析调用由`CloseReader`自行打开短只读事务。

### 3.2 保留单一核算与分析来源

- M1 `calculate_session()`继续是唯一基础核算函数。
- M3 `reader/metrics/evidence/diagnostics/scenarios`继续是唯一分析实现。
- 新增应用服务层只做类型化分派、统一默认值和错误包装，不复制计算。
- Web渲染层只能读取应用服务返回的结构化字段。
- MCP层改为调用相同应用服务，不再单独维护异常包装和默认行为。

## 4. 共同参数与结果契约

### 4.1 应用服务

新增`src/analysis/service.py`，提供与八个工具一一对应的方法：

1. `list_close_versions`
2. `query_performance`
3. `compare_performance`
4. `get_session_evidence`
5. `compare_close_versions`
6. `get_metric_rules`
7. `diagnose_performance`
8. `simulate_scenario`

`src/analysis/schemas.py`补充共同常量和类型：

- `CloseRef`、`AnalysisScope`、分页、排序、比较、证据与假设结构。
- `DEFAULT_MODE = current`。
- 默认利润口径与排序指标为`final_profit`；同时展示双利润。
- 默认分页`offset=0, limit=20`，最大100。
- `CONTRACT_VERSION = m3-contract-v1`。
- 允许的指标、分组、模式、证据主题、诊断规则和假设枚举。

领域模块继续负责实际校验；不为了共享契约再引入一套重复的校验框架。

### 4.2 统一返回

共同服务的成功和业务错误使用统一信封，必填字段为`status`、`contract_version`和生成时间`as_of`。`scope`、核算与分析规则版本只在已验证且适用于该请求时返回，不为缺库、未知规则等错误填入默认核算版本。以下是已验证范围的成功结果示例，不是所有响应的必填模板：

```json
{
  "status": "ok",
  "contract_version": "m3-contract-v1",
  "as_of": "...",
  "scope": {},
  "accounting_rule_version": "m1-decimal-half-up-v1",
  "analysis_rule_version": "m3-analysis-v1",
  "data": {},
  "summary_text": "..."
}
```

业务错误保留现有`error.code/message/next_action`；HTTP状态码是传输信息，不改变共同服务的JSON错误契约。进入共同服务后的相同业务请求，成功结果、业务错误码和业务信息必须一致。

协议和传输层错误单独验收：例如HTTP JSON解析失败、媒体类型不支持、Host/Origin不合法，以及MCP在进入共同服务前拒绝参数。这些错误不强求相同响应包装或共同服务信封，不得为通过一致性测试而放宽协议校验。

金额始终使用后端返回的整数分、两位人民币元文本和币种；比率使用十进制字符串、百分比文本以及分母不适用原因。浏览器不得从`cents`自行生成利润合计，也不得对分页明细求全量总数。

### 4.3 八项HTTP接口

| HTTP接口 | 对应共同服务/MCP工具 | 说明 |
|---|---|---|
| `GET /api/analysis/versions` | `workbench_list_close_versions` | 月份状态和版本目录 |
| `POST /api/analysis/performance` | `workbench_query_performance` | 汇总、筛选、排序和排名 |
| `POST /api/analysis/compare-performance` | `workbench_compare_performance` | 期间或两个业务范围比较 |
| `POST /api/analysis/evidence` | `workbench_get_session_evidence` | 单场证据下钻 |
| `POST /api/analysis/compare-versions` | `workbench_compare_close_versions` | 同月两个关账版本比较 |
| `POST /api/analysis/rules` | `workbench_get_metric_rules` | 指标公式、分母和限制 |
| `POST /api/analysis/diagnostics` | `workbench_diagnose_performance` | 固定规则问题定位 |
| `POST /api/analysis/scenario` | `workbench_simulate_scenario` | 非持久化条件测算 |

期间比较必须使用两个完整`AnalysisScope`；版本比较必须使用同一月份的两个明确版本。前端、HTTP路由和文字标签中都不能把二者统称为“版本/期间对比”。

`/api/analysis/*`下的POST接口仅接收`application/json`，设置小于工作台上传限制的独立请求上限；继续校验本机Host和同源Origin。因为没有状态修改，不复用M2表单CSRF字段，但不得因此放宽Host、Origin或数据库路径约束。

## 5. 页面与版本交互

首版继续采用与M2一致的服务端渲染，不引入前端框架。`analysis_ui.py`只接收共同服务返回的payload并生成HTML；JSON API和页面处理器调用同一个应用服务。`analysis.js`只负责复制文本、展开区域和必要的控件交互，不承载业务计算或版本选择逻辑。

页面表单采用以下明确路径，不通过浏览器自行计算或请求本机MCP：

- 查询、筛选、分页、证据和两类比较使用`GET /analysis`，以明确的区域参数和类型化范围参数选择操作；页面处理器解析参数并直接调用共同服务，返回HTML。
- 条件测算使用独立的`POST /analysis/scenario`页面处理器，接收`application/x-www-form-urlencoded`表单，在服务端转换金额及假设参数，调用共同服务并返回包含原输入和测算结果的HTML。
- 页面POST与JSON API分别解析各自媒体类型，均设置请求上限并校验Host/Origin；二者都在`workbench.connect()`之前分派，既不复用M2写操作处理链，也不互相通过HTTP调用。
- JSON API继续只接受其规定的输入类型；页面表单无需JavaScript执行fetch或更新金额结果。八项JSON接口之外的页面处理器不增加新的业务能力。

### 5.1 一级导航和旧链接

新增规范页面：

- `/months`：月份总览。
- `/workbench?month=...&step=...`：M2结算工作台。
- `/analysis?month=...&version=...&mode=...`：M3经营分析。

迁移时先把M2内部GET表单、分页、返回链接和历史链接统一改为`/workbench`。兼容规则：

- 旧的`/?month=...`、`/?step=...`及带现有M2筛选参数的链接继续渲染或重定向到相同M2上下文。
- 裸`/`在兼容路由完成并通过测试后再指向`/months`。
- M2所有POST动作路径保持不变，操作后的当前步骤、筛选、锚点和提示不得丢失。
- `/template`、`/export`和历史Excel链接保持兼容。

关账成功页增加“进入经营分析”入口，携带当次`month/version/mode=current`。历史版本页入口携带`mode=history`，不能靠颜色推断历史身份。

### 5.2 分析页信息架构

首屏只展开：

1. 经营概览：后端总额、双利润、利润率、场次数、实际日期范围和达人构成。
2. 重点场次：最终亏损；经营盈利但最终亏损；主要成本构成作为解释。

按需展开：

3. 场次/达人列表及证据下钻。
4. 期间比较。
5. 关账版本比较。
6. 条件测算。
7. 指标口径说明。

页面顶部固定展示当前范围，不只展示月份：模式、全部CloseRef、场次/达人/日期筛选、排序利润口径、关账时间和数据截止时间。筛选后标题必须写“筛选范围”，并同时显示筛选场次数；不得继续把概览称为“全月”。

### 5.3 版本状态规则

- 页面和每个API请求都携带明确`CloseRef`和`mode`，不请求含义不明的“最新金额”。
- `mode=current`中版本变化返回`VERSION_CHANGED`；页面丢弃本轮尚未整体提交显示的结果，展示阻断提示和“查看新版本/保留历史V1”选择。
- `mode=history`固定读取原版本，同时查询版本目录；存在新版时显示“正在查看历史V1，当前有效版本为V2”，绝不自动切换。
- 月份重开返回`MONTH_REOPENED`，显示“月份已重开，当前无有效关账结果”；只允许用户明确转为历史查看。
- 同一页面需要组合概览与诊断时，页面组合层先核对返回的CloseRef集合、模式和核算规则；全部分析调用完成后、提交HTML响应前，通过共同服务的版本目录能力统一复核涉及月份的状态与当前版本，并记录`version_checked_at`。当前模式发现重开或换版时丢弃本轮成功片段，展示阻断提示；历史模式保留原版金额，按复核结果更新历史身份。
- 刷新、下钻、比较和测算请求继续携带原明确引用，并重新校验状态；不沿用上一页面的“当前有效”判断。
- 期间比较页面分别展示基期和当期的完整版本身份；版本比较分别展示V1/V2，不能只依赖页面顶部单个版本标签。

页面明确显示“版本状态截至本次校验时间有效”。固定引用保证金额不混版，状态标签反映最后一次校验时点；复核后或页面打开后仍可能发生重开，不承诺实时更新。首版不增加后台轮询、服务端页面会话或分析缓存。

## 6. 重点场次的共同语义

当前诊断同一场次可命中多项规则，`major_components`也会逐场产生解释项，因此不能把`items`数量显示为“异常场次数”。

调整共同诊断结果，在完整筛选范围计算后增加`data.summary`：

- `final_loss`：返回规则执行状态和全范围亏损场次数。
- `operating_profit_final_loss`：返回规则执行状态和全范围场次数，明确`subset_of=final_loss`。
- `attention_session_count`：两条关注规则均已运行时，返回按场次去重后的并集数量；不包含`major_components`。任一规则未运行时该完整并集数量为`null`，注明未完整运行，不能把部分结果称为全部关注场次。
- 规则使用`status=executed/not_run`；只有已执行且无命中才返回`count=0`，未执行返回`count=null`并注明原因。
- `major_components`继续作为每场解释数据，不计入异常或关注数量。摘要不返回所有场次编号。

重点场次明细与摘要使用相同的全范围结果：后端在每条关注规则内按最终结算利润从低到高排序，同额按明确场次引用稳定排序，然后分页；本页明细携带场次引用、双利润金额和证据引用。不能保留旧的“规则＋场次编号”顺序却只在摘要另列金额排名。看板分别按规则请求对应明细页，不让解释项挤占重点场次页；多个规则一起请求时先按固定规则顺序，再按各规则内部次序分页。

分页只影响展示项，不改变全范围计数。摘要与明细均由`diagnostics.py`生成，Web和MCP原样复用，前端无需获取全量列表后重排。界面文字使用“需要关注”或具体规则名称，不使用“系统判断异常”“健康分”等标签。

## 7. 复制分析引用

复制内容由后端依据已经验证的返回范围生成，前端只执行复制，不从控件自行拼造版本身份。

单场引用包含：

- 当前/历史模式及实际状态。
- 月份和版本。
- 场次、达人或日期筛选范围。
- 经营复盘利润/最终结算利润口径或排序口径。
- 明确“保持该版本，不自动切换最新版”。

期间比较引用包含两侧完整范围；版本比较引用包含同月两个版本；测算引用原样包含类型化假设和“非实际结算结果”说明。来源名称、SKU和用户备注只作为转义后的业务数据，不能进入Harness指令段。

首版只提供“复制引用”和复制成功反馈，不建设浏览器到Codex/Claude Code的自动跳转、会话创建或客户端探测。

## 9. 一致性测试矩阵

每个共同能力至少覆盖以下四条路径：

| 能力 | 直接服务 | MCP | HTTP JSON | 浏览器展示 |
|---|---|---|---|---|
| 版本目录 | 结构基线 | 同主体 | 同主体 | 状态/版本文字正确 |
| 经营汇总 | 金额与比率基线 | 同主体 | 同主体 | 只展示后端文本 |
| 诊断 | 规则及去重摘要基线 | 同主体 | 同主体 | 不把items当场次数 |
| 证据 | 分页及引用基线 | 同主体 | 同主体 | 无额外原始字段 |
| 期间比较 | 两Scope与桥基线 | 同主体 | 同主体 | 两侧版本完整 |
| 版本比较 | 两Version基线 | 同主体 | 同主体 | 历史身份完整 |
| 规则 | 公式和限制基线 | 同主体 | 同主体 | 可按需展开 |
| 测算 | 基准/假设/差额基线 | 同主体 | 同主体 | 不在JS重算 |

一致性断言针对进入共同服务的同一业务请求，忽略允许变化的传输包装和生成/校验时间；业务字段、默认参数、金额、比率、排名、分页、规则执行状态及命中、版本身份和业务错误码必须相同。HTTP解析和访问校验、MCP协议参数拒绝等服务外错误各自验收，不要求相同包装。页面表单先在服务端转换为相同类型化参数后比较，缺库或未知规则的错误不得含未经验证的核算版本。

额外安全回归：

- 分析请求不调用`workbench.connect()`。
- `CloseReader`仍只查询`months/closes`。
- 缺库不创建，旧库不迁移，请求不新增表。
- 浏览分析和测算前后数据库内容一致。
- HTTP输入不能指定数据库路径、SQL、文件输出或URL。
- M2导入、批量确认、关账、重开和Excel测试全部继续通过。

## 10. 完成定义

本轮只有同时满足以下条件才算完成：

1. 浏览器可以从关账结果进入结构化M3看板，完成六类分析操作。
2. Web与MCP复用同一应用服务和契约，且有自动化一致性证据。
3. 分析路由被测试证明没有经过工作台写连接入口。
4. 页面不会静默切换版本或混合多次请求结果；响应前复核状态并标明校验时间，刷新、下钻和测算重新校验，不承诺已打开页面实时更新。
5. 重点场次按场次去重、后端金额排序后分页，计数覆盖全范围；未运行不当作零命中，规则解释项不冒充异常数量。
6. 浏览器不调用模型、不执行财务计算，条件测算不落库。
7. M2原流程、旧链接兼容和正式Excel无回归。
8. 财务BP使用合成数据完成一次页面试用并确认术语、筛选和下一步清晰。

本轮完成后，再根据真实使用决定是否启动“内部共享部署”独立设计，不把认证和网络部署提前塞入本次看板整合。
